# 未决项对比方案（P3-5、P3-7）

> 写作风格：ASD-STE100 简化技术写作。一句一个意思。主动语态。用简单现在时。

## 1. 用途

本文档列出两项**缺目标证据**的未决项。每项给出候选方案、代价与判定方法。

项目负责人选定方案后，开发者按方案落地，并更新 `PROGRESS.md`。

两项都不阻塞当前功能。现状可用。

## 2. P3-5 · 台标动效的像素公式

### 2.1 现状

`src/logo_anim.rs` 输出 6 种动效，每种 10 帧无损动画 WebP。

| 效果 | 状态 |
| --- | --- |
| `breathe` | 逐字节对齐目标。增亮曲线 `[0,2,3,4,5,5,4,3,2,0]` |
| `diagonal` | 近似 |
| `vertical` | 近似 |
| `bounce` | 近似 |
| `spot` | 近似 |
| `glow` | 近似 |

5 种近似的差别在亮度增益公式。帧数、尺寸、编码参数已对齐。

### 2.2 证据缺口

目标二进制的像素公式未解。仅凭截图无法反推：动效是 10 帧，任取一帧都有多解。

### 2.3 候选方案

| 方案 | 做法 | 代价 | 结果 |
| --- | --- | --- | --- |
| A | 保持近似 | 0 | 视觉接近，逐字节不一致。不影响播放与显示 |
| B | 补目标逐帧导出，反推公式 | 一次取证：目标容器内对同一张源图跑 6 种效果，导出 60 帧 | 可逐字节对齐。需要目标环境可用 |
| C | 只做能验证的部分 | 0 | 与 A 相同。不做 |

### 2.4 判定方法（选 B 时）

1. 在目标容器内放一张 256×256 的纯白 PNG。
2. 对 6 种效果各生成一次动画。
3. 用 `anim_dump` 或等价工具导出每一帧为 PNG。
4. 逐帧比对：整体均值、逐行均值、逐列均值、质心。
5. 按剖面反推增益函数，写进 `logo_anim.rs`。

判定标准：6 种效果的 60 帧全部逐字节相等。

### 2.5 建议

选 A。理由：

- 台标动效只影响面板展示，不影响播放链路。
- 逐字节对齐的收益是「比对数字好看」，不是可用性。
- 目标环境取证成本高于收益。

若后续要做，选 B，并且一次做完 5 种。不要逐种做。

## 3. P3-7 · `dash-timeshift/status` 的时长键名

### 3.1 现状

`GET /panel/api/dash-timeshift/status` 返回每条回看频道：

```json
{"group_id":"g","channel_id":"c","hours":4,"segments":12,"mode":"dash"}
```

`hours` 的取值按频道类型决定：

- `dash_timeshift=true` → 取 `dash_timeshift_hours`。
- 否则取 `timeshift_hours`。

取值正确。**键名**未对拍。

### 3.2 证据缺口

目标的响应键名有两种可能：

- 统一键 `hours`。
- 分键 `timeshift_hours` 与 `dash_timeshift_hours`。

现有夹具只覆盖 `timeshift_hours`。`dash_timeshift` 频道的响应未抓取。

### 3.3 候选方案

| 方案 | 返回 | 代价 | 风险 |
| --- | --- | --- | --- |
| A | `hours`（现状） | 0 | 若目标是分键，调用方读不到 |
| B | 分键 `timeshift_hours` / `dash_timeshift_hours` | 小 | 若目标是 `hours`，调用方读不到 |
| C | 三个键都返回 | 小 | 响应多字段。字段严格比对时记 1 项差异 |

本实现没有第二个消费方。面板不读这条接口的 `hours`。

### 3.4 判定方法

在目标容器内建一个 `dash_timeshift=true, dash_timeshift_hours=4` 的频道，请求该接口，看键名。

一次请求即可定案。

### 3.5 建议

选 A，并保持现状。理由：

- 三种方案的风险相同，都是「猜」。
- C 会引入确定的字段差异，A 和 B 只在猜错时才有差异。
- 现有 `hours` 与 `docs/design/03-http-contract.md` §回看 的写法一致。

若拿到目标环境的 5 分钟，改选 B 或 C 前先做 §3.4 的一次请求。
