# 手工验收测试

本目录存放**由项目负责人手工执行**的验收测试。

自动化测试见 `cargo test` 与 `scripts/smoke-*.sh`。两者不重叠：

- 自动化测试证明**代码按设计退出**。
- 本目录的测试证明**真实机器上服务能用**。

> 写作风格：ASD-STE100 简化技术写作。一句一个意思。主动语态。用简单现在时。

## 1. 谁来执行

| 角色 | 做什么 |
| --- | --- |
| 项目负责人 | 按本文档在真实 VPS 与 CDN 控制台执行 |
| 开发者（Claude） | 维护本文档，修复不通过的项 |

这些测试需要外部环境，开发机替代不了：

- 一台真实 VPS（1 vCPU，小内存，小磁盘）。
- 一个可配置的 CDN 控制台。
- 真实上游或本地夹具。

## 3. 前置条件

通用前置，每份文档另有补充。

| 项 | 要求 |
| --- | --- |
| 操作系统 | Linux。amd64 或 arm64 |
| 权限 | 首次安装要 `root` |
| 网络 | 能访问该 VPS 的面板端口 |
| 工具 | `curl`、`shasum`（或 `sha256sum`）、`tar` |
| 二进制 | 来自 `v*` tag 的发布产物，不是本地构建 |

不支持的组合：macOS、Windows、32 位。

## 4. 怎么记录结果

每份文档末尾有记录模板。执行时复制一份到 `docs/tests/runs/`，文件名用日期：

```
docs/tests/runs/2026-10-30.md
```

一条测试一个结论。三种取值：

| 取值 | 含义 |
| --- | --- |
| 通过 | 现象与「预期」完全一致 |
| 不通过 | 现象与「预期」不一致。必须在同一行写实际现象 |
| 未验证 | 条件不具备。必须写缺什么 |

不要写「基本通过」。不通过就写不通过。

## 5. 不通过时怎么办

1. 按该文档的「失败时怎么报」一节收集证据。
2. 把证据和结论贴进 `docs/tests/runs/<日期>.md`。
3. 交给开发者。开发者在 `PROGRESS.md` 立一条缺口。

## 6. 与自动化的边界

下表说明哪些结论**不能**只靠自动化测试：

| 结论 | 为什么自动化测不了 |
| --- | --- |
| 安装后服务自动启动 | 依赖目标机的 init 系统（systemd 或 OpenRC） |
| 面板版式对齐 | 需要人眼看层级 |
| 磁盘回收在真实磁盘上收敛 | 需要真实可用空间下降 |
| 64 MB 实例长时间不 OOM | 需要真实内存压力与 24 小时时长 |
| CDN 命中 | 需要一个真实 CDN |
| 1 vCPU 下不抖动 | 需要真实单核机器 |

其余行为都有自动化覆盖，不必手工重复。
